# 性能和资源

## 预算怎么定

- 只设一组高的"灾难线"，只守平台拒收、浏览器崩溃和已经不可玩这三条边界

- 一条东西只留一条预算线

- 写进断言的数字要注明来历，没推导过就明说"这是哨兵值"

- 按比例砍东西之前，先问分母是什么

- 替人定帧率目标时，理由要查代码，不凭通识

- 预算数字连推导过程一起写进路线图

- 没有实测缺口就别为性能删画面

## 贴图和显存

- 贴图预算至少分下载体积和显存两条，显存用 `textures_vram` 单独管

- "什么时候改用 KTX2 压缩贴图"写成一个条件：显存那条线先红的那天

## 绘制次数和三角形

- 大量小构件按空间分区加材质合批

- 算绘制次数时把阴影 pass 算进去

- 限制实例数的同时把索引压紧

- 会越积越多的东西（轮胎印、雪迹）用实例化加固定容量

- 大量重复的小物件共用几种形状，加随机旋转和缩放

- "氛围"和"玩法"分开摆

- 沿路线撒东西按长度密度分配，不要总量截断

- 动态光源尽量少

- 曲面多的模型要一起看碰撞开销

## 卡顿和预热

- 开局前（加载画面里）把整条路线会用到的着色器程序和贴图上传一次做完，包括阴影

- 预热是否到位，用"加载完成后新冒出来的着色器程序数"判断，不用帧时间

- 这条路线上的所有地标模型都在加载画面里下载、解析、编好着色器

- 物理引擎第一次推进时才给所有碰撞体建查找结构

- 撞一下就要做的计算，按“一次撞击多少毫秒”量

- 卡顿要在有窗口的真浏览器里量，无头浏览器量不出来

- 被弹窗完全盖住的场景停止每帧重画

- GPU 画面读回 CPU 很贵，能不做就不做

- 手机上先拆“每帧时间花在哪”，再决定减什么

- 会动的物理实体要能睡着

## 下载和打包

- 体验门槛卡"第一次能开车之前要下载多少"，总量只用来发现异常膨胀

- 按 itch.io 的真实上限定体积预算：解压后总量 500 MB、文件数 1000、单文件 200 MB、路径 240 字符

- 体积统计只数一份产物，并拿真实数字对账

- 同一份数据只请求一次，同一个模型只下载一次

- 选车页之类的展示用离线渲染的缩略图，不加载完整模型

- 小地图用自己导出的矢量路网，不用第三方地图瓦片

- 音效用 WebAudio 合成，预算留给几何和贴图

- 改了资源内容就必须改缓存版本号，用测试把两者绑在一起

- 开发和预览服务器一律发 `Cache-Control: no-store`

## 流式加载

- 切片请求带代际号，过期到达的直接丢

- 卸载时先删碰撞体，再释放几何

- 卸载多留一段滞回距离，失败有限次重试后放弃并报错

- 路面下加一张常驻安全网

- 等路的车放开前要有回滞

## 释放和泄漏

- 每个生命周期入口（比赛、选车预览等）都显式 `dispose` 并释放 WebGL 上下文，查真实的 GL 句柄数，不查 three.js 对象数

- 物理刚体泄漏只查"车辆名下"的刚体和关节

- 删一个功能要顺藤摸瓜：入口、管线、数据接口一起删

- 关掉可选玩法时，连它的资产加载一起关

- 停 `<video>` 要 `pause()` 再 `load()`

- 大块数据放 IndexedDB，不塞 localStorage；拆细存档键时回头检查所有上限

## 手机档

- 手机单独一档默认值，"自动画质"在手机上直接锁低档，不做运行时升档

- 手机和平板只带 2 辆 AI 对手，桌面不封顶

- 手机显存紧，从低档起步，并准备好 WebGL 上下文丢失的出路

- 首屏在手机上保持最轻

## 启动

- "启动完成"以第一个可用画面为准

- 在 HTML 里内联一个极小的启动壳，监听入口脚本本身的下载失败并提供重试

## 怎么量才诚实

- 性能缺口必须从目标硬件实测反推

- 每个性能数字都同时记：渲染器字符串（真 GPU 还是软件）、画质档、机位、路段和机器

- 软件渲染和浏览器面板隐藏时的帧率只当回归探测

- 嵌入式浏览器里 `requestAnimationFrame` 可能不跑，让游戏自己在画面上报帧率

- 截图要在同一次 WebGL 渲染回调里读，或打开 `preserveDrawingBuffer`

- 声称"全程"的测量，把"跑完了"本身写成断言

## 仓库本身的体积

- 截图、录像这类证据存成 WebP，并用一条总量上限测试挡住
